# 网络网关：捕获、分流与出口

网关是整套体系的脊柱：所有出境流量在这里被接住、分类、判决。本文覆盖捕获双通道、规则相位、探测对抗、链式出口、以及自建网关与 GUI 客户端两种部署形态。

## 一、捕获双通道

流量进入网关有两条独立通道，互为备份：

| 通道 | 原理 | 覆盖范围 |
|---|---|---|
| **TUN 虚拟网卡** | 内核层把系统默认出口指向虚拟网卡，全部流量无感接管 | 一切进程，无论是否配合 |
| **系统代理** | 操作系统设置告示"流量发往 127.0.0.1:混合端口" | 遵守告示的应用（浏览器为主） |

纪律：**两个至少开一个，TUN 是主力**。危险状态只有一种 = 双关（killswitch 名单内的应用仍 fail-closed，名单外全部裸奔）。两者同开无害（系统代理流量经回环进网关，TUN 不捕获回环，无双重代理）。TUN 创建需要管理员权限——网关进程必须提权运行，非提权实例会静默无 TUN 地半死。

## 二、规则相位（顺序即安全）

规则自上而下首命中即停。最终形态（相位序号 = 优先级）：

```
① REJECT 纯遥测域名（sentry/datadog/oaistatsig/copilot collector 等）
② 进程 DIRECT（国内日常应用白名单，逐进程标注用途，生命线置顶）
③ 进程 MATCH（可疑进程整体送链：防自报家门型探测）
④ 域名 MATCH（境外 AI/开发/云服务目标域）
⑤ 域名 DIRECT（确认真用的国内服务，最小化）
   私网 IP-CIDR（内网/认证系统）
   GEOSITE,CN / GEOIP,CN（国内域名与地址直连）
   境外 UDP 拒绝（住宅链无 UDP 时的闭合）
   MATCH 兜底 → 代理组（第 103 条左右，其后规则永不参与匹配）
```

铁律：

- **match 类规则全部位于兜底 MATCH 之前；兜底必须是最后一个有效规则。** MATCH 之后的任何规则都是死代码——订阅自带的大规则集放在 MATCH 之后即为隔离，无需清理但不可指望它生效。
- **同域双目标冲突一律 MATCH 优先**（一条域名不可能既直连又送链；判错方向 = 主动喂真实 IP）。
- **顺序错误的代价是方向性的**：探测域排在直连前 = 应用探测你时拿到真实 IP（主动泄漏）；MATCH 排在 DIRECT 后 = 国外 AI 应用借国内域探测定位。相位表就是按"先掐遥测、再保生命线、再按进程整个端走、再按域名、其余国内、最后兜底"的泄露危害排序。
- 直连白名单每条标注归属与用途，定期按"日志零命中"清理。
- 链式目标组书写：一律写底层单跳组名，由内核自动升级链式；直接写 relay 组名会被物化成嵌套封装组。
- 规则在相位内按类型聚合 + 字母序整理（生成器确定性输出，两次构建 md5 一致），审查与 diff 友好。

## 三、进程探测对抗（"软件用国内域名定位我"怎么办）

把攻击手法拆开：国外软件想知道你的位置，但它的流量全走代理（看到东京）；它的花招是诱导你直连访问它控制的国内站，国内站日志记下真实 IP，再经代理汇报完成拼接。三层防御：

1. **进程 MATCH 相位**：被点名进程的全部流量（不分域名）强制送链——它 ping 国内站也是从东京出口发的，拼接结果定位到东京。
2. **防火墙 killswitch**（见 killswitch.md）：名单内应用除回环/fake-ip 外一切出站拒绝——它连发起直连的资格都没有。
3. **兜底 MATCH + 国内人设面**：未被点名的软件访问国内域名走 GEOSITE,CN 直连，国内服务器看到真实 IP——这是主动保留的暴露面，它只能得出"此人在中国"（国内人设的一部分），得不出城市/楼栋，更拼不出境外行为（那对它是全程不可见的）。

**管理员权限不改变以上任何一条**：TUN、防火墙、DNS 劫持都在内核层，应用无法选择绕过网卡。

## 四、链式出口

```
本机 →（入口协议 SS/VMess 等）→ 中转 VPS（不限流量、稳定、抗干扰）
     →（住宅 HTTP/SOCKS5）→ 住宅 IP（目标网站看到的身份）
```

分工：VPS 负责"运出去"（住宅端口通常不对本地网开放，且入口需要大带宽不限量）；住宅负责"看起来像真人"（目标服务看到的是家庭宽带 ASN，欺诈分低）。代价：全程延迟 = 两段 RTT 之和；住宅侧带宽与 UDP 支持决定上限（无 UDP 时以"境外 UDP 拒绝"规则闭合，fail-closed）。

自建中转的部署与测速方法见 `scripts/` 附带的部署参考（选型：机房近本地、协议抗干扰、带宽不限或高额）。

## 五、两种部署形态

### A. 自建裸网关（推荐主形态）

裸跑 mihomo 系内核 + 配置文件为唯一真源 + 浏览器面板（metacubexd/zashboard 本地部署）。

- **配置治理**：`config.yaml` 就是真相，由生成器脚本确定性产出（规则相位内自动整理）；热加载 API 即时生效；每次改动 git/timestamp 双备份。
- **守护**：计划任务开机自启（登录触发/highest/幂等：已运行跳过、杀旧防双开）、统一管理入口脚本（状态/启动/回退/同步/面板）。
- **面板**：zashboard/metacubexd 本地 ui 目录，URL 参数预填后端（hostname/port/secret），首次配置存 localStorage。
- **内核/面板自动升级**：均关闭。升级=手动+升级后四键核验（见 ops-runbook.md）。

### B. GUI 客户端形态（回退/轻量备选）

FlClash/Clash Verge 一类：界面友好，但配置真源在客户端内部存储，`config.yaml` 是**生成物**——文件直改会被升级/存储迁移回写蒸发，规则新增必须走 UI 编辑器，订阅自带名单需隔离于兜底 MATCH 之后。存储模型、注入实验法、IPv6 双关口径、端口跟随等细则统一见 `proxy-dns-architecture.md` §3（该节是 GUI 形态的唯一细则来源，本文不重复）。

### 选型结论

同一内核，能力面同构；差异全在治理。自建形态多出：文件级可审计、确定性生成、隔离订阅名单、无界面层漂移。GUI 形态保留为回退与应急（其配置同样要按本体系四键核验后才是合格备胎）。
